# Пайплайн — CRM-прототип для онлайн-школы

Один файл `pipeline-crm-prototype.html` — статический HTML/CSS/vanilla JS прототип
без бэкенда. Все данные живут в памяти (JS-переменные), сбрасываются при
перезагрузке страницы. Цель файла — зафиксировать UX и бизнес-логику перед
реальной разработкой, а не быть production-кодом.

Открывается просто как файл в браузере, зависимостей нет (кроме шрифтов
Google Fonts через `@import` в `<style>`).

## Структура файла

Три части в одном файле:
1. `<style>` — вся вёрстка, CSS-переменные в `.crm-root` (цвета, кегль)
2. HTML-разметка — скелет (topbar, вкладки, контейнеры под вьюхи, `#modal-root`)
3. `<script>` — вся логика, один самовызывающийся IIFE, без модулей/фреймворков

## Модель данных (в памяти, не персистится)

- `stages[]` — 10 этапов обучения, каждый `{ name, days }`. `days: null` у
  последнего этапа (без нормы). **Редактируется** в реальном времени из
  Админки (длительность) и из Kanban (название колонки, admin-only).
- `curators[]` — `{ id, name, color, login, password, blocked,
  canMoveOthers, canReassign, seeLeads, seeStats }`. Права и блокировка —
  чисто фронтовая имитация, реальной авторизации нет.
- `leads[]` — `{ id, username, name, bullets[], price, pingAt, archived }`
- `students[]` — `{ id, name, stage (index в stages), curatorId, enteredAt
  (дата входа на текущий этап), paused, timeline[], bullets[], postpayPct,
  comments[], cohortIdx (индекс в standardCohorts) }`
  - `timeline[]` — единая лента событий: `{type:'stage', stage, enteredAt,
    exitedAt}` и `{type:'curator', from, to, at}`. Текущий этап добавляется
    в неё виртуально при рендере (`exitedAt: null`).
- `standardCohorts[]` — последние 6 календарных месяцев, `{ label, date }`.
  `cohortIdx` у ученика изначально = ближайший месяц к его реальной дате
  старта (`cohortOf()`), но дальше редактируется независимо (админ меняет
  вручную в модалке когорты) — то есть это **отчётная**, не жёстко связанная
  с историей метка.

## Ключевая бизнес-логика

- `isStuck(s)` — превысил ли ученик норму текущего этапа. Всегда `false`
  для paused и для этапов без нормы.
- `healthTier(s)` → `'green' | 'yellow' | 'red' | 'paused'` — зона 🟡
  начинается от 70% нормы, 🔴 — после 100%.
- `plannedStageForElapsed(elapsedDays)` — если бы шли ровно по нормативам,
  на каком этапе (индексе) должны быть через N дней. Используется и для
  разовой карточки ученика (нет), и для когортной воронки.
- `plannedCompletion(s)` — прогноз даты завершения: остаток нормы текущего
  этапа + сумма норм всех следующих. `null`, если на паузе.
- Когортная воронка (`renderStats`, доп. вкладка): % достижения этапа
  считается по факту (`s.stage >= idx`), календарная группировка — по
  `cohortIdx`. НО «на плане / отстаёт» в модалке когорты считается
  **индивидуально**, от личной даты старта каждого ученика
  (`cohortOf(s)`), а не от 1-го числа месяца когорты — иначе тех, кто
  зашёл в конце месяца, ложно считало отстающими.

## Права доступа (симуляция)

Селектор «Смотреть как» вверху переключает `currentRole` (`'admin'` или
id куратора). Все `canSeeTab()` / `canMoveStudent()` / `canReassignCurator()`
проверки идут от него. Это **имитация** ролевой модели для демонстрации
UX — реальных сессий/токенов нет, любой может открыть консоль браузера и
поменять `currentRole` напрямую.

⚠️ Пароли кураторов в Админке хранятся и показываются в открытом виде —
осознанное упрощение для прототипа. В реальной системе так делать не
стоит, правильный паттерн — сброс пароля, а не его просмотр.

## Известные ограничения / что предстоит решить в реальной разработке

- Нет бэкенда, БД, реальной авторизации — всё выше нужно спроектировать
  заново под сервер (Postgres/что угодно + сессии).
- Нет реального приёма лидов из Telegram-группы (обсуждали AI-парсинг
  сообщения с подтверждением — в прототипе лиды статичные демо-данные).
- Нет уведомлений/напоминаний о пинге — только визуальный бейдж в UI.
- `standardCohorts` жёстко строится от текущей даты (последние 6 месяцев) —
  на реальном бэкенде это, вероятно, должна быть таблица когорт, а не
  вычисляемый на лету список.
- Кнопка "+ Лид" использует `prompt()` — заглушка, не полноценная форма.

## Как продолжать дальше

Разумный следующий шаг — не переписывать этот файл, а вынести модель
данных (`stages`, `curators`, `students`, `leads`, вся бизнес-логика
`isStuck/healthTier/plannedStageForElapsed/...`) как есть в качестве
спецификации на бэкенд, а фронт пересобрать на нормальном стеке
(React/Vue + реальный API). UX-решения (какие плашки, какие подсказки,
какой порядок сортировки карточек) можно брать из этого файла почти
дословно — это то, что уже прошло несколько итераций фидбека.
